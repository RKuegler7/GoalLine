## PHASE E: Goal to league flow, invites, and people search (most urgent)

1. Goal to league flow. After a user creates a goal, show a clear next step: "Play it with friends?" with three choices: Create a league, Join a league (enter an invite code), or Keep it solo ("against the line"). Creating a league from there pre-fills the league's name and category from the goal and attaches the goal to the league. Do the same from the Clubhouse entry point. No dead ends: a user should never create a league and then see nowhere to invite people.
2. Invites. Every league has an Invite section, shown right after creating the league and always reachable from the league page:
   - A shareable invite link and a short code, each with a copy button and the native share sheet on mobile where available.
   - Invite by email (send through the existing Brevo mail setup if configured) or by username, which sends an in-app invite.
   - Invite tokens are random and unguessable, can be revoked and regenerated by the league owner, optionally expire (default 14 days), and have an optional max-uses cap.
   - A join page at the invite link: shows the league name, goal type, member count and owner, asks the visitor to sign in or register first if needed, then lets them join and pick or create their goal for that league.
   - League owners see pending invites and current members, and can remove a member or revoke an invite.
   - Leagues show members and a visible "Invite friends" button whenever the league has fewer than 4 members.
3. People search. Add a search box in the Highlights area, the friends page and the invite flow. It searches by name or username, and by exact email. Results show only avatar, name and username, with buttons: Add friend, Invite to league, View. Include a "People in your leagues" list on the friends page. Privacy: add a setting "Let people find me by name" (default on); when off, the user only appears for exact username or exact email. Rate limit the search and never show emails in results. Friend requests, accept and decline all work from the results.
4. Tests: invite token creation, expiry, revocation, max-uses, joining via a link, joining while signed out, non-owner cannot manage invites, search respects the discoverable setting and never leaks emails, goal-to-league redirect for all three choices.

## PHASE F: Goal-specific intake questions

Goal: GoalLine asks smart questions specific to the goal before building the roadmap, so the plan is tailored to the person, like a good coach would.

1. Flow. After the user names a goal, category and target date, call the Claude API to generate 5 to 8 intake questions specific to that goal. Return structured JSON. Each question has: id, text, type (single choice, multiple choice, number with unit, short text, scale 1 to 5), options if relevant, and an optional "why we ask" line. Show them one at a time or as a clean short form, mobile friendly, with a progress indicator, a Skip option and an "I'm not sure" option on every question.
2. Quality. The questions must be genuinely goal-specific. Examples to put in the prompt for the model:
   - Running or a race: current weekly mileage and longest recent run, recent race times, how many days per week available, injuries or pain history, experience level, preferred surface, whether they have a coach or watch.
   - Strength or a lift PR: current maxes, training experience, equipment access, days available, injuries.
   - Academic or an exam (CPA, MCAT, bar): exam sections and test date, hours per week available, prior attempts and scores, weakest areas, study materials owned, preferred study times.
   - Thesis or writing: current word count or stage, deadline structure, advisor milestones, hours available.
   - Challenges like 75 Hard: which rules, past attempts, obstacles.
   For any other goal, infer sensible questions about starting point, constraints, time available and obstacles.
3. Safety for physical goals. Include one question about injuries or health considerations. Never give medical advice or diagnoses. Plans must use conservative progression (for example, no more than about 10 percent weekly mileage increases for beginners), include rest days, and show a short note: "GoalLine plans are general guidance, not medical advice. Check with a doctor if you have health concerns." If answers suggest a risk (for example recent injury), the plan starts more conservatively and says why.
4. Use the answers. Store the answers with the goal (a goal_intake table or JSON column) and pass them to the Goal Decomposer so the roadmap reflects them. Show a short "Your plan is built from: ..." summary on the goal page, with the key answers and an Edit answers button that triggers a plan refresh (Phase G).
5. Fallbacks. If the API call fails or times out, use built-in fallback question sets per category so the flow never blocks. Validate and sanitize all model output. Cap lengths. Log failures without exposing API errors to the user.
6. Tests: JSON validation of generated questions, fallback behavior on failure, answers saved and passed to the decomposer, skip and "not sure" handling.

## PHASE G: Update and refine the roadmap

Goal: a place to easily change the roadmap and tell GoalLine ideas and specifics, not just name the goal.

1. Add a "Refine your plan" box on the goal page: a free-text prompt with example chips such as "I can only train 4 days a week", "Add a long run on Sundays", "Make weeks lighter, I have finals", "Focus more on my weakest section", "Move my deadline up a week". Submitting sends the current roadmap, the intake answers and the instruction to the Claude API, which returns an updated roadmap in structured JSON.
2. Preview before saving. Show the proposed changes as a clear diff: tasks added, removed, moved, and point or schedule changes, plus a one-line explanation of why. The user taps Accept or Discard. Never overwrite the plan silently.
3. Guardrails. Only future, not-yet-completed tasks and weeks change. Past check-ins and completed tasks are never altered. Keep planned points sensible for fair scoring: if the refined plan changes total planned points for the current week, apply the change starting next week unless the current week has no check-ins yet. Enforce the existing caps and the safety rules from Phase F.
4. Manual editing too. The user can directly add, edit, reschedule, reorder or delete future tasks and milestones with simple forms, within the same guardrails, and every change is logged.
5. Plan history. Save each accepted version with a timestamp and a short summary, and show "Plan history" with the option to restore a previous version for future weeks.
6. Tests: diff generation, accept and discard, past tasks untouched, scoring unaffected for completed weeks, restore, validation of malformed model output, failure fallback.

## PHASE H: Easier habit and recurring-task check-offs

Goal: recurring objective tasks should be quick to manage and unambiguous to check off. First inspect the current habit UI and data model and tell me what is hard about it, then fix it.

1. Make every recurring task define an objective completion rule when it is created or planned:
   - Checkbox (did it or not).
   - Number with a threshold (for example run at least 2 miles, 25 practice questions).
   - Minutes or duration with a threshold.
   - Optional proof (photo) per Phase A.
   Show the rule right on the task, for example "Run 2+ miles" so it is clear what counts.
2. Cadence types: every day; specific days of the week; or "X times per week" (for example 4 of 5 runs). Weekly-target habits count progress toward the target (shown as "3 of 4 this week") instead of marking a missed day as a failure, and planned points are spread across the target.
3. Better check-off UI:
   - A "Today" view listing everything due today with one-tap check-offs and quick number entry.
   - A week grid (days across, habits down) with one-tap toggling for today or yesterday only, in line with the no-backfill rule.
   - A "Mark all done" for simple checkbox tasks, and swipe or tap targets that are large on mobile.
   - Clear states for done, due, upcoming, and rest day; encouraging copy, never red warning badges.
4. Streaks and consistency. Show a calm "days on the line this week" consistency indicator and keep existing streaks working. Frame everything around the process: "One more day on the line."
5. Reminders. Use existing nudges and Brevo email for a daily reminder at a time the user picks, with an opt out.
6. Tests: threshold rules (below, at and above), weekly-target progress, no check-in beyond today or yesterday, scoring unaffected for existing data, grid and today view show the right items.
